# 大数据分析能力评估

## 一、当前简化架构的能力边界

### 实时处理层（满足 ✅）
| 能力 | 状态 | 说明 |
|------|------|------|
| 日志解析 | ✅ | 支持 JSON/Syslog/CEF |
| 实时告警 | ✅ | 阈值/单事件/关联规则 |
| 基础统计 | ✅ | COUNT/SUM/AVG 按时间窗口 |
| 存储查询 | ✅ | TimescaleDB 支撑日亿级写入 |

### 大数据分析层（不足 ⚠️）

| 需求 | 当前能力 | 差距 |
|------|---------|------|
| **多维度复杂聚合** | SQL 聚合 | 无法支撑超复杂查询 |
| **亚秒级全文搜索** | 基础 LIKE | ES 性能 100x+ |
| **历史数据挖掘** | 简单查询 | 无 ML/AI 分析能力 |
| **跨数据集关联** | 单表 JOIN | 多源关联性能差 |
| **PB级存储** | 有限 | 需要分层存储 |

### 各层职责

| 层级 | 组件 | 数据量 | 查询延迟 | 用途 |
|------|------|--------|---------|------|
| **实时** | Redis Streams | 当前 1小时 | <100ms | 实时告警 |
| **热数据** | TimescaleDB | 最近 30天 | <1s | 仪表盘/趋势 |
| **温数据** | ClickHouse | 30天-1年 | 1-5s | 复杂分析/报表 |
| **冷数据** | ES | 全量索引 | <1s | 全文搜索/调查 |
| **归档** | S3/OSS | 1年以上 | 小时级 | 合规/审计 |

## 三、各组件对比

### 时序数据库选型

| 指标 | TimescaleDB | InfluxDB | ClickHouse |
|------|-------------|----------|------------|
| **写入性能** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **查询性能** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **SQL 支持** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ |
| **集群能力** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **运维复杂度** | 低 | 中 | 中高 |

**推荐**: 温数据层使用 **ClickHouse**，分析性能最强

### 分析引擎选型

| 引擎 | 特点 | 适用场景 |
|------|------|---------|
| **ClickHouse** | 列式存储向量化执行，聚合性能最强 | 实时 OLAP、仪表盘 |
| **Apache Doris** | MySQL 协议，Join 能力强 | BI 报表、多表关联 |
| **StarRocks** | 极速 Join，秒级查询 | 复杂分析、Ad-hoc |

**推荐**: **ClickHouse** 或 **Apache Doris**

## 四、改造后的架构建议

### 方案 A：轻量级（推荐中小规模）

```
数据源 → 统一处理器 → TimescaleDB → Grafana/仪表盘
                      ↓
                   定期同步 → ClickHouse → 复杂分析
```

**适用**: 日志量 < 1000万/天

### 方案 B：企业级（推荐大规模）

```
数据源 → 统一处理器 → TimescaleDB (实时)
                      ↓
                   Kafka (缓冲)
                    ↙        ↘
            ClickHouse      Elasticsearch
              (分析)          (搜索)
                    ↘        ↙
                  S3/OSS (归档)
```

**适用**: 日志量 > 5000万/天

## 五、具体改造建议

### 1. 添加 ClickHouse 分析层

```python
# 分析查询示例
ANALYSIS_QUERIES = {
    # Top 攻击源
    "top_attackers": """
        SELECT src_ip, count() as cnt
        FROM alert_logs
        WHERE time >= now() - INTERVAL 24 HOUR
        GROUP BY src_ip
        ORDER BY cnt DESC
        LIMIT 10
    """,
    
    # 按小时趋势
    "hourly_trend": """
        SELECT toStartOfHour(time) as hour, 
               severity, 
               count() as cnt
        FROM alert_logs
        WHERE time >= now() - INTERVAL 7 DAY
        GROUP BY hour, severity
        ORDER BY hour
    """,
    
    # 资产风险排名
    "asset_risk": """
        SELECT dst_ip, 
               countIf(severity='high') as high_cnt,
               count() as total_cnt,
               high_cnt / total_cnt as risk_ratio
        FROM alert_logs
        WHERE time >= now() - INTERVAL 30 DAY
        GROUP BY dst_ip
        HAVING total_cnt > 100
        ORDER BY risk_ratio DESC
        LIMIT 20
    """
}
```

### 2. 添加 Elasticsearch 搜索层

```yaml
# Logstash 管道配置
```

## 七、结论

**当前简化架构能否满足大数据分析？**

| 需求 | 答案 | 说明 |
|------|------|------|
| 实时告警 | ✅ 完全满足 | 延迟 <100ms |
| 基础仪表盘 | ✅ 满足 | 30天内数据查询 |
| 复杂分析报表 | ⚠️ 需增强 | 需要添加 ClickHouse |
| 全文搜索调查 | ❌ 不足 | 需要保留 ES |
| PB级存储 | ❌ 不足 | 需要冷热分层 |

**建议**:
1. **中小规模** ( <1000万/天): 当前架构 + 定期同步到 ClickHouse
2. **大规模** ( >5000万/天): 引入 ClickHouse + 分层存储
3. **搜索需求强**: 保留 Elasticsearch
